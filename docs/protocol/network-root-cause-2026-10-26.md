# MAX Desktop — исследование общей причины TLS/WS_CONNECT (26.10.2026)

## Подтверждённые факты

Пользователь проверил установленную v0.1.8, **без номера и кода**:

| Транспорт | Адреса | Последний этап |
|---|---|---|
| TCP через системный прокси | api2.oneme.ru, api.oneme.ru, api-tg.oneme.ru | TLS_HANDSHAKE: EOF до получения серверного сертификата |
| TCP напрямую | Те же три домена, дополнительные IP | TLS_HANDSHAKE: EOF до получения серверного сертификата |
| WebSocket .NET | ws-api.oneme.ru:443 | WS_CONNECT, вложенный TLS/EOF |
| WebSocket Chromium/WebView2 | ws-api.oneme.ru:443 | WebSocket.onerror до открытия соединения |

Все попытки завершились **до команды INIT и AUTH_REQUEST** (за исключением анонимных проверок на иных хостах в GitHub Actions). Телефон и SMS здесь ни при чём.

На других компьютерах в среде GitHub Actions получены успешные TLS и ответы на анонимный INIT для TCP и для WebSocket .NET/Chromium. Следовательно, адреса и базовый протокол способны работать, но результат **не переносится на сетевой маршрут владельца**.

## Ошибка прежнего подхода

Вместо независимой диагностики доступности инфраструктуры MAX **на конкретном Windows-компьютере пользователя** последовательно менялись TLS-корневой сертификат, порядок адресов, прокси, тип TCP/WebSocket и сетевой движок браузера. Все эти изменения использовали инфраструктуру под одним доменным суффиксом **oneme.ru**.

Из имеющихся доказательств наиболее экономно объясняется общий отказ **до прикладного протокола**: DNS, маршрут, локальный прокси/VPN, фильтрация по SNI, перехват TLS, сетевой экран либо политическая/географическая маршрутизация. Конкретный вариант не установлен, поэтому «обнаружена блокировка» писать нельзя.

Ошибка проверки сертификата клиента не может объяснить EOF **до получения сертификата**. Ошибки SMS/INIT не могут объяснить сбой до успешного TLS. Для Chromium `onerror` недостаточно точен: браузер не выдаёт JS информацию, была ли проблема TLS или HTTP 403.

## Решающий тест без нового установщика

**В обычном браузере пользователя** открыть
https://ws-api.oneme.ru/websocket

Это HTTP GET вместо WebSocket Upgrade. Любой **HTTP 400/403/404/426** подтверждает, что до сервера дошли по HTTPS и браузер получил HTTP-ответ. Никакой код SMS не отправляется.

Если браузер выдаёт `ERR_SSL_PROTOCOL_ERROR`, `ERR_CONNECTION_RESET` либо `PR_END_OF_FILE_ERROR`, то ошибка есть **вне MAX Desktop** — искать прокси, DNS, сетевой маршрут или фильтрацию домена `oneme.ru`.

Открыть https://web.max.ru/ как контроль для инфраструктуры другого домена; загрузка одной лишь страницы **не доказывает**, что WebSocket API работает.

Для независимой проверки системы Windows запустить в обычной командной строке:

```text
curl.exe -I --max-time 15 https://ws-api.oneme.ru/websocket
```

Здесь не отключается проверка сертификата и не передаются учётные данные. Если curl выдаёт HTTP-код, TLS установился; если (35), TLS/EOF, то сбой повторяется вне WPF-клиента. Ошибка (60) — отдельная проблема доверия к сертификату, не равная «сертификата вообще не было».

### Матрица интерпретации

| Обычный браузер | curl.exe | Интерпретация |
|---|---|---|
| Нет HTTPS | Нет HTTPS | Проблема воспроизводится независимо от нашего приложения; проверить маршрутизацию, DNS, прокси, фильтрацию, альтернативную сеть |
| HTTP-ответ | Ошибка TLS | Отличается путь браузера: системный прокси, расширение VPN, политика процесса и доверенные сертификаты |
| HTTP-ответ | HTTP-ответ | Сетевая доступность подтверждена; затем исследовать WebView2 внутри приложения, его прокси, заголовки Upgrade и политику процессов |
| Нет HTTPS | HTTP-ответ | Разные браузерные и системные маршруты/профили, проверить настройки браузера |

Важно: HTTP 400 или 403 здесь **не означает успешную авторизацию**; это только подтверждение HTTPS. Не публиковать в журнале приватные номера телефонов, SMS, токены, Cookie или заголовки Proxy-Authorization.

## Дальнейшие действия

Не выпускать следующий установщик только ради очередной замены TLS-движка. Сначала получить результат независимого теста **с компьютера пользователя**. Затем принять одно конкретное исправление, ориентированное на фактический слой ошибки.

QR-авторизация исключена по требованию пользователя.

## Реальная независимая проверка пользователя — 26.10.2026, ~13:38 МСК

Пользователь выполнил предложенную проверку на том же компьютере Windows и передал три изображения:

1. **Яндекс Браузер** по `https://ws-api.oneme.ru/websocket?utm_source=chatgpt.com` сообщает «Не удаётся установить соединение с сайтом. Соединение было неожиданно прервано». Параметр utm_source был добавлен платформой открытия ссылки, **не является подтверждённой причиной**.
2. В средствах разработчика выбран запрос `websocket?utm_source=chatgpt.com`, отмеченный ошибкой. Поле заголовков ответа пустое. Следовательно, успешного HTTP-ответа на снимке **не получено**.
3. **Системный curl.exe в PowerShell** независимо от браузера вызвал `curl.exe -I --max-time 15 https://ws-api.oneme.ru/websocket` **без параметра utm_source**, получил точный текст `curl: (35) schannel: failed to receive handshake, SSL/TLS connection failed`. Значит, параметр отслеживания не объясняет общий сбой.

Вывод: **сетевой сбой TLS воспроизводится вне MAX Desktop и до авторизации**. Необходимо искать ограничение или неисправность сетевого маршрута/системы/прокси/сервера для данного подключения. Эти факты **не доказывают конкретного виновника** (провайдер, регион, SNI, VPN, локальный фильтр, сервер), но делают крайне маловероятной гипотезу о единственной ошибке сериализации или интерфейса MAX Desktop.

### Следующая единственная приоритетная проверка

Не меняя MAX Desktop, подключить **тот же компьютер Windows к независимому интернет-каналу** (например, мобильной точке доступа телефона; желательно без стороннего VPN) и повторить `curl.exe -I --max-time 15 https://ws-api.oneme.ru/websocket`. Сопоставить:

- Новая сеть даёт HTTP-ответ (включая 400/403/426): исходный маршрут/провайдер/прокси/политика сети препятствует HTTPS.
- Новая сеть даёт такую же TLS/Schannel ошибку: подозрение смещается к Windows, системной фильтрации/прокси, общему VPN и программам безопасности либо доступности сервиса для двух маршрутов. Нужна дальнейшая локализация; не утверждать, что это точно Windows.
- Если доступен официальный клиент MAX на том же компьютере и он устанавливает сеанс, нужно установить реальные домены/транспорт его соединений. Это не опровергает отказ HTTPS на `ws-api.oneme.ru`.

**Переходить к следующему установщику только после доказательного изменения, устраняющего конкретный сетевой сбой.** Текущий релиз v0.1.8 оставлен без изменений.

## Сопоставимый независимый тест на Windows Runner — 26.10.2026

После подтверждённого локального `curl (35)` три задания повторно запущены через GitHub (все успешно):

- TCP: https://github.com/lvlaksim1/max-desktop/actions/runs/40248116311 — TLS 1.3 и SESSION_INIT от `api2.oneme.ru`, `api.oneme.ru`, `api-tg.oneme.ru`.
- .NET WebSocket: https://github.com/lvlaksim1/max-desktop/actions/runs/40253115470 — анонимный SESSION_INIT.
- Chromium/WebView2: https://github.com/lvlaksim1/max-desktop/actions/runs/40255463057 — анонимный SESSION_INIT.

В существующий процесс `.github/workflows/max-websocket-probe.yml` добавлена проверка утилитой Windows `curl.exe`. URL и HTTP-метод HEAD совпадают с локальным опытом; заголовки не выводятся в журнал.

Исправленное задание: https://github.com/lvlaksim1/max-desktop/actions/runs/40315701059

- `RUNNER_CURL_EXIT_CODE=0`
- `RUNNER_CURL_HTTP_STATUS=403`
- Анонимный `SESSION_INIT` в этом же задании успешен.

HTTP 403 здесь означает доступный HTTPS-сервер с отказом на анонимный запрос, но не успешную авторизацию. В отличие от Runner, аналогичная команда на ПК владельца ранее давала `curl: (35) schannel: failed to receive handshake`, без HTTP.

Вывод: различие условий исполнения подтверждено. Участки среды (ПК и сети) различаются одновременно; эта пара результатов не доказывает конкретного виновника (провайдер, маршрут, VPN/прокси, локальная фильтрация, настройки Windows или серверная политика). Следующий контролируемый опыт — тот же ПК владельца через независимый интернет-канал. До локализации причины не требуется выпускать новую версию приложения.

Первый запуск дополненного процесса 40315485293 завершился синтаксической ошибкой сценария PowerShell. Выражение исправлено; повторный запуск 40315701059 успешно прошёл. Ошибка первого запуска не связана с TLS.

## Проверки непосредственно на Windows владельца с включённым системным VPN — 26.10.2026

Подключена штатная интеграция с приватным `lvlaksim1/pc-runner-gateway`: MAX Desktop разрешён в политике шлюза, установлен официальный Client Kit 1.2, PowerShell диагностика исполняется из неизменяемого SHA через саморазмещённый Windows Runner. Успешный host.ping — Issue №392/393.

Результаты, полученные **именно с пользовательского Windows при включённом VPN**:
- [№394](https://github.com/lvlaksim1/pc-runner-gateway/issues/394): DNS `ws-api.oneme.ru` разрешается в два IPv4; TCP 443 доступен. `curl` к `ws-api.oneme.ru` и `web.max.ru` — ошибка 35; .NET HTTP — SendFailure.
- [№395](https://github.com/lvlaksim1/pc-runner-gateway/issues/395): системный HTTP-прокси обнаружен. Обычный и явно настроенный прокси выдают `curl 35` к обоим MAX-доменам. Контрольные github.com, mail.ru, www.microsoft.com через доступный маршрут возвращают HTTP 200, а через тот же прокси github.com/mail.ru — HTTP 200.
- [№396](https://github.com/lvlaksim1/pc-runner-gateway/issues/396): HTTP CONNECT через системный прокси к `ws-api.oneme.ru` возвращает 200, но конечная TLS-сессия обрывается (curl 35) при автоматической версии, TLS 1.2 и TLS 1.3. Для GitHub тот же HTTP-прокси даёт CONNECT 200 и конечный HTTP 200.
- [№397](https://github.com/lvlaksim1/pc-runner-gateway/issues/397): прокси на loopback, его обслуживает процесс Xray; присутствует TUN-интерфейс, переменные HTTP_PROXY/HTTPS_PROXY/ALL_PROXY/NO_PROXY не заданы.
- [№398](https://github.com/lvlaksim1/pc-runner-gateway/issues/398): подтверждён Xray, но управляющее VPN-приложение по ограниченной проверке не определено.

**Подтверждённый уровень сбоя:** после TCP и HTTP CONNECT, но до получения конечного HTTP-ответа по TLS, причём только на проверенных адресах MAX. **Не доказано**, что конкретно вызывает закрытие TLS: выбор маршрута Xray, удалённый VPN-выход, фильтрация или политика на стороне MAX. Изменения TLS-движка приложения без решения доступности сети не обоснованы.

[Прямое требование владельца] VPN нельзя отключать, клиент должен работать при постоянно работающем VPN. Любое изменение маршрутизации или конфигурации VPN подлежит отдельному согласованию, тесты проводятся при включённом VPN. Релиз по-прежнему v0.1.8.
## Рабочая альтернатива VPN-маршруту и v0.1.9 — 26.10.2026

Владелец разрешил приложению вести трафик MAX любым способом, при строгом запрете изменения конфигурации системного VPN.

Локальная заявка [#399](https://github.com/lvlaksim1/pc-runner-gateway/issues/399): при работающем VPN обычный HTTPS MAX curl (35), но curl с привязкой к физическому IPv4 получил HTTP 403 от ws-api.oneme.ru и HTTP 200 от web.max.ru. Заявка [#400](https://github.com/lvlaksim1/pc-runner-gateway/issues/400): ручное TCP/TLS подключение с проверкой сертификата и WebSocket Upgrade HTTP 101. Заявка [#402](https://github.com/lvlaksim1/pc-runner-gateway/issues/402): выбор физического интерфейса подтверждён.

Реализован PhysicalMaxWebSocketChannel на C# (.NET 8): SocketsHttpHandler.ConnectCallback, Socket.Bind к выбранному интерфейсу, UseProxy=false, проверка сертификата и имени MAX. Автовыбор теперь Physical → Edge → .NET → TCP только до возможной отправки SMS. [Windows Actions 40322276206](https://github.com/lvlaksim1/max-desktop/actions/runs/40322276206) подтвердил реальный анонимный SESSION_INIT нового модуля. [Windows CI 40322590907](https://github.com/lvlaksim1/max-desktop/actions/runs/40322590907) и [выпуск 40323017999](https://github.com/lvlaksim1/max-desktop/actions/runs/40323017999) завершились успешно; опубликованы v0.1.9 Setup/Update/SHA-256, предыдущий релиз удалён.

Ожидается проверка SESSION_INIT **установленной v0.1.9 именно на ПК владельца при включённом VPN**, после чего один запрос SMS и дальнейшая авторизация. Факт реального LOGIN пока не установлен.
