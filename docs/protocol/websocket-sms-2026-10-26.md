# MAX Desktop — вход через WebSocket без QR (26.10.2026)

## Цель

Приёмка Windows MAX Desktop на машине владельца: прямые TCP/TLS-подключения к `api2.oneme.ru`, `api.oneme.ru`, `api-tg.oneme.ru` обрывались до получения сертификата даже с системным прокси. Это **не доказывает ошибку протокола авторизации**, но делает необходимым независимый транспорт.

Владелец **исключил QR-авторизацию**. Добавлен вход по номеру телефона через WEB/WebSocket как альтернативный путь, не меняя интерфейс и установку WPF.

## Проверенные независимые реализации

- [huxuxuya/python-max-client](https://github.com/huxuxuya/python-max-client), `python_max_client/client.py`: `wss://ws-api.oneme.ru/websocket`, заголовок `Origin: https://web.max.ru`, JSON-протокол версии 11. Методы `send_code` (opcode 17), `sign_in` (18), `login_by_token` (19), `_send_hello_packet` (6).
- [MaxApiTeam/PyMax](https://github.com/MaxApiTeam/PyMax): отдельный `WebSocketTransport`, `WsProtocol`; реализация последовательности SMS/пароль/токен и сохранения сеанса.
- [Tellarion/webmaxsocket](https://github.com/Tellarion/webmaxsocket): вход по SMS и 2FA, альтернативные транспорты. QR не используется в MAX Desktop.

## Архитектура

- `MaxWebSocketCodec`: в отличие от TCP, отправляет JSON `{ver:11,cmd:0,seq,opcode,payload}`.
- `NativeMaxWebSocketTransport`: `ClientWebSocket` с системным прокси, проверкой TLS MAX, Origin и User-Agent; `INIT(6)` → `START_AUTH(17)` → `CHECK_CODE(18)` → при необходимости пароль `115` → `LOGIN(19)`. Запросы сериализованы, ответ сопоставляется с `seq`/`opcode`; нет ложного входа, если сервер не подтвердил LOGIN.
- `HybridMaxTransport`: выбор «Автоматически / WebSocket / TCP». При автоматическом входе сначала WebSocket; TCP может использоваться как резерв **только если WebSocket не установил соединение или не прошёл анонимный INIT**. После отправки запроса SMS автоматический повтор через другой транспорт запрещён.
- `MaxSavedSession.Transport`: новая необязательная метка `WEB`/`TCP`. Старые хранилища без поля продолжают использовать TCP. Токен хранится с прежней шифровкой Windows DPAPI.
- QR-подтверждение **не реализовано**.

## Проверки

- [GitHub Actions 40253115470](https://github.com/lvlaksim1/max-desktop/actions/runs/40253115470): Windows-исполнитель подтвердил защищённое WebSocket-подключение и серверный ответ `SESSION_INIT` **без номера, кода, QR и токенов**.
- `tests/MaxDesktop.WebSocket.Smoke`: протокол JSON v11, SMS-пакет, обработка ошибок, обратная совместимость сохранённых сеансов и выбор транспорта без сети.
- Windows CI компилирует WPF и запускает все протокольные и файловые тесты. Тесты не отправляют проверочные SMS.
- Реальная доставка кода по номеру и завершение авторизации с конкретного компьютера владельца **не подтверждены**. Сервер может потребовать капчу или альтернативную проверку; приложение не выдаёт ложный успех.

## Поведение приложения Windows

- Крестик главного окна — `Hide()` и работа в трее, без закрытия приложения или потери сеанса.
- Системная кнопка «Свернуть» — обычное сворачивание в панель задач.
- Двойной щелчок по значку трея — восстановление окна.
- Правый щелчок по трею — «Открыть MAX Desktop» и «Выход», явный выход освобождает ресурсы.
- Межпроцессный Mutex + сигнал активации: повторный запуск не создаёт второй экземпляр; открывает существующий.
- Обновитель использует явное завершение, которое обходит обработчик «крестик в трей». Иначе установленное обновление могло бы зависнуть в ожидании работающего процесса.

## Непроверенные функции

- Успешный запрос SMS на живом номере, условия капчи, 2FA и полный вход.
- Синхронизация чатов и отправка сообщений.
- Фактическое взаимодействие кнопок трея на пользовательской Windows; компиляция не заменяет графическую приёмку.

## Приёмка v0.1.9 и ручная VK Captcha в v0.1.10

На компьютере владельца с включённым системным VPN в установленной v0.1.9 режим «Автоматически» подтвердил физическое защищённое WebSocket-соединение и SESSION_INIT. Затем START_AUTH(17) получил серверную ошибку: «Проверка не пройдена, попробуйте ещё раз». Это происходит после успешного TLS, так что прежняя транспортная неисправность не является объяснением.

По независимому исследованию https://github.com/pr0bel1230/max-api-docs/blob/main/protocol/auth.md и наблюдениям веб-версии MAX, сервер может требовать VK ID CAPTCHA_REQUEST (opcode 224) с {source:"auth",identifier:phone}, возвращать link на id.vk.ru/not_robot_captcha, после чего человек проходит испытание и полученный captchaToken передаётся в VERIFICATION_REQUEST (opcode 17). Фраза ошибки указывает на такую необходимость, но конкретный внутренний код ошибки на аккаунте владельца пока не измерен. Пробник с локального ПК при неизменном VPN подтвердил доступность id.vk.ru (Issue https://github.com/lvlaksim1/pc-runner-gateway/issues/403).

Реализация v0.1.10:
- После подтверждённого серверного отказа на опкоде 17 приложение запрашивает 224 **без автоматического повторного SMS**.
- Допустимый HTTPS-адрес проверки открывается в изолированном WebView2, пользователь вручную выполняет задание.
- При получении и валидации captchaToken приложение продолжает текущую сессию, добавляет поле captchaToken в один следующий запрос 17; токен в лог не записывается. Отмена закрывает ожидание без отправки кода.
- Физический интерфейс/VPN не меняются, QR-вход не добавлен.
- Windows CI 40325552079 подтвердил WPF сборку и автономные проверки человеческой капчи, отмены, отсутствия автоматических дублей SMS. GitHub Actions выпуск 40325831275 — успешно, два установщика v0.1.10 и SHA-256 опубликованы, предыдущие выпуски удалены.

Не подтверждено реальной приёмкой: появление CAPTCHA-виджета, успешный возврат токена именно от VK ID, приём следующего START_AUTH сервером, SMS/код/2FA/LOGIN. Следующий контрольный опыт — один запуск выдачи кода в установленной v0.1.10 при включённом VPN. Не публиковать личные данные и токены.

## v0.1.11 — обработчик результата VK Captcha SDK

В установленной v0.1.10 владелец подтвердил появление VK Captcha и успешное нажатие галочки «Я не робот» (зелёная галочка), но окно не закрывалось. Причина на уровне кода: самостоятельно созданный iframe и предположения о формате postMessage, тогда как `@vkid/captcha` предоставляет собственный обработчик `CaptchaPublicEvents.SUCCESS` с `{token}`.

В v0.1.11 внедрён pinned `@vkid/captcha@2.0.0`: `CaptchaWidget.render({link,container:"#captcha"})`, подписка на SUCCESS, токен передаётся в локальный мост WebView2 только после события и не более одного раза. Установщик включает собранный SDK, а не загружает его при авторизации из CDN. Определение CAPTCHA_REQUEST(224), защита от автоматического повторения SMS и маршрут через физический IPv4 с работающим VPN сохранены.

Сборка/автономный тест передачи события `SUCCESS → solved`: https://github.com/lvlaksim1/max-desktop/actions/runs/40330935479 . Выпуск: https://github.com/lvlaksim1/max-desktop/actions/runs/40331289185 . **Настоящий VK callback и дальнейший SMS/LOGIN не подтверждены пользователем** — требуется отдельная приёмка v0.1.11.

## v0.1.12 — ошибочное сообщение после введённого SMS и застрявший сеанс

Реальная проверка владельца на v0.1.11: после прохождения VK Captcha SMS приходит, пользователь вводит код и нажимает подтверждение, но окно остаётся и показывает «Запрос принят. Введите код, полученный от MAX». После закрытия и повторного открытия при попытке анонимной проверки получено «Нельзя проверить соединение во время активной авторизации».

Статическая проверка установила две причины:
1. NativeMaxWebSocketTransport.VerifyCodeAsync перехватывает ошибки CODE_ENTER(18) и LOGIN(19), возвращая сохранённое AwaitingVerification с AuthResult.Error. LoginWindow.ShowResult безусловно заменял Error на предыдущий информационный статус. Нельзя делать вывод о принятии кода по прежнему сообщению.
2. Close оставлял ожидающую авторизацию в памяти, потому что CancelPendingLoginAsync ранее сбрасывал только AwaitingCaptcha, а закрытие окна его не вызывало.

В v0.1.12 исправлено отображение стадии WS_CHECK_CODE и WS_LOGIN, а при закрытии незавершённого окна LoginWindow вызывает сброс AwaitingVerification/AwaitingPassword/AwaitingCaptcha без воздействия на Connected. Автономные тесты эмулируют отклонённый код, отклонённый LOGIN после успешного кода и анонимный Probe после сброса; CI https://github.com/lvlaksim1/max-desktop/actions/runs/40340814912 — success. Выпуск https://github.com/lvlaksim1/max-desktop/actions/runs/40341203011 — success; установленная версия ожидает проверки.

**Неизвестно:** фактический ответ сервера после SMS. Следующая приёмка v0.1.12 должна показать конкретную безопасную ошибку; токены/номера/коды не выводить.

## Действительный серверный ответ после SMS и сравнение с официальным клиентом (26.10.2026)
Снимок владельца MAX Desktop v0.1.12 подтвердил: после ручной VK Captcha, получения SMS и ввода кода протокол WEB opcode 18 CHECK_CODE вернул серверное сообщение `Логин ограничен. Требуется установить 2FA`. Этот отказ нельзя интерпретировать как неуспешный TLS, проблему капчи или доказанное отклонение SMS-кода.
Владелец указал, что в оригинальном MAX новая (по его описанию) авторизация проходит без капчи и запроса 2FA; не известно, какой платформы это приложение и каким было состояние доверенного устройства. Официальная справка MAX (https://help.max.ru/help/account/dostup_k_prophilyu/kak_voiti_v_prophil_max_esli_on_uzhe_est) описывает требование установки облачного пароля на активном устройстве для входа на другое, если пароль ещё не установлен. Это обоснованная, но пока не доказанная для данного аккаунта гипотеза различия политик WEB/доверенного устройства.
Не применять несогласованные способы обхода 2FA, не подменять идентификатор доверенного устройства; исследовать только подтверждённые пользовательские сценарии. Следующий шаг — установить, какую оригинальную программу и новое/старое устройство сравнивает пользователь. Версия v0.1.12 не изменена.
