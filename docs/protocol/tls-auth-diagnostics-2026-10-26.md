# Ошибка авторизации: EOF и проверка TLS (26.10.2026)

## Сообщение пользователя

При попытке получить проверочный код в MAX Desktop v0.1.2 окно входа показывало:

`Received an unexpected EOF or 0 bytes from the transport stream`

Сообщение было выдано до ответа на запрос кода и **не является доказательством неверного номера телефона**. Номер телефона, коды, пароли и токены в публичной документации отсутствуют.

## Подтверждённые результаты диагностики

### Проверка Windows TLS без учётных данных

Сборка GitHub Actions [40245569406](https://github.com/lvlaksim1/max-desktop/actions/runs/40245569406):

- DNS для `api2.oneme.ru` работает, TCP-подключение к 443 открывается.
- На чистом Windows-исполнителе стандартная проверка TLS выдаёт `RemoteCertificateChainErrors`.
- Попытка TLS 1.2 со стандартным хранилищем приводит к той же ошибке.

Сборка [40245884044](https://github.com/lvlaksim1/max-desktop/actions/runs/40245884044):

- При проверке сертификата с дополнительным **Russian Trusted Root CA** (публичный `rootca_ssl_rsa2022.crt`, используемый в исследованной библиотеке PyMax) цепочка подтверждается.
- Подключение с дополнительным центром сертификации завершено успешно, TLS 1.3, `TLS_AES_128_GCM_SHA256`.
- Корневой сертификат применяется **только к MAX TCP-клиенту** и не устанавливается в доверенные сертификаты Windows.
- Проверка имени сервера, срока действия, цепочки доверия и отзыва сохранена; никакие ошибки сертификата не игнорируются.

### Проверка анонимной инициализации

Сборка [40246081737](https://github.com/lvlaksim1/max-desktop/actions/runs/40246081737):

- Отправлен один запрос `SESSION_INIT` (код 6) через проверенное TLS-соединение.
- Телефон, SMS-код, пароль и токен пользователя в тесте не использовались.
- Получен и расшифрован корректный ответ `command=1, opcode=6`, `flags=1`, длина тела 222 байта.
- Получено поле `callsSeed`, необходимое для `AUTH_REQUEST`.

## Исправления в MAX Desktop

- `MaxTlsCertificateValidator` добавляет ограниченный доверенный центр сертификации для защищённого соединения MAX, **не отключая проверку подлинности**.
- `NativeMaxTransport` сообщает этап сбоя: `TCP_CONNECT`, `TLS_HANDSHAKE`, `SESSION_INIT`, `AUTH_REQUEST` и последующие.
- Ошибка EOF больше не интерпретируется как отказ авторизации или неправильный код.
- Добавлена автоматическая проверка сертификата на отсутствие допуска пустого сертификата и несовпадения имени.

## Ограничение исследования

Это воспроизведение ошибки проверки сертификата в среде GitHub Windows и успешная проверка анонимного `SESSION_INIT`. Оригинальный EOF на компьютере владельца мог быть вызван другим сетевым узлом или промежуточным устройством. Авторизация по его номеру, выдача SMS, обработка ответа `AUTH_REQUEST`, сохранение токена и восстановление сеанса всё ещё требуют пользовательской проверки.

## Повторная ошибка на компьютере пользователя: `TLS_HANDSHAKE / EOF`

После установки версии 0.1.3 пользователь сообщил **тот же тип обрыва**, теперь локализованный на этапе `TLS_HANDSHAKE`. Это доказывает, что одного дополнительного корневого сертификата недостаточно, чтобы обеспечить подключение в пользовательской сети. До `SESSION_INIT` и `AUTH_REQUEST` программа не доходит.

Дополнительный независимый Windows-тест [40246937237](https://github.com/lvlaksim1/max-desktop/actions/runs/40246937237) сравнил:

- Системное доверие, автоматический TLS: ошибка цепочки.
- Дополнительный корневой сертификат, автоматический TLS: **TLS 1.3 успешно**.
- Дополнительный корневой сертификат, **явный TLS 1.2/1.3** (как в v0.1.3): **TLS 1.3 успешно**.

Следовательно, нельзя утверждать, что неверная настройка выбора TLS — установленная первопричина пользовательского обрыва. Причина может зависеть от сетевого маршрута, Windows/Schannel, промежуточных устройств или недоступности конкретного IP-узла. Полученные проверки не позволяют определить это удалённо.

## Усиление диагностики в v0.1.4

- TLS использует системный выбор поддерживаемой версии при неизменной проверке имени и цепочки сертификата.
- При ошибке подключения клиент последовательно пробует не более трёх IP-адресов, возвращённых DNS для `api2.oneme.ru`, с паузой не менее пяти секунд между попытками.
- Для каждого адреса проверка сертификата выполняется по **имени узла**, а не по IP. Отключение TLS/проверки имени не допускается.
- Новый пункт `Проверить соединение (без номера)` использует тот же код подключения и один анонимный `SESSION_INIT`. Он не отправляет телефон, SMS-код, токен или сохранённую учётную запись.
- Сообщение об ошибке содержит этап соединения, число попыток и факт предъявления серверного сертификата, без персональных данных.

**Приёмка ещё не завершена:** нужна проверка из пользовательской сети на установленной версии 0.1.4. Успешный тест на GitHub Windows не означает гарантированного подключения на устройстве пользователя.

## Пользовательская приёмка v0.1.4 и проверка трёх резервных узлов

На Windows в установленной версии 0.1.4 кнопка `Проверить соединение (без номера)` завершилась ошибкой `TLS_HANDSHAKE / EOF`. Серверный сертификат не был получен **ни в одной из трёх попыток** к основному узлу `api2.oneme.ru`. Таким образом, проблемы `SESSION_INIT`, номера телефона и запроса SMS здесь исключены: до них клиент не доходит.

Независимое испытание Windows GitHub Actions [40248116311](https://github.com/lvlaksim1/max-desktop/actions/runs/40248116311) проверило три имени сервера (без телефонного номера и без учётных данных):

| Узел | TLS с проверкой имени и цепочки | Анонимный `SESSION_INIT` |
|---|---|---|
| `api2.oneme.ru` | TLS 1.3 успешно | `command=1`, `opcode=6`, `callsSeed` |
| `api.oneme.ru` | TLS 1.3 успешно | `command=1`, `opcode=6`, `callsSeed` |
| `api-tg.oneme.ru` | TLS 1.3 успешно | `command=1`, `opcode=6`, `callsSeed` |

В MAX Desktop v0.1.5 добавлена последовательная проверка проверенных серверов. Сначала перебираются разные имена серверов, затем дополнительные возвращённые DNS-адреса: не более **двух IP на узел, шести попыток суммарно**, интервал между попытками не менее пяти секунд. В TLS всегда передаётся имя соответствующего сервера и сохраняется обязательная проверка сертификата. Диагностика показывает только имена узлов, этап и безопасный тип ошибки; не записывает IP-адреса, номера, коды и токены.

В окне входа добавлена возможность отмены длительного подключения. Исправлено закрытие окна после подтверждения авторизации.

**Результат теста на GitHub не гарантирует соединение из пользовательской сети.** Если все три имени продолжают обрываться до сертификата, необходимо исследовать локальную маршрутизацию и фильтрацию соединения, а не менять структуру SMS-запроса.
