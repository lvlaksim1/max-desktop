# MAX Desktop — сверка мобильного протокола и платформы запуска
Дата: 2026-10-27. Основание: пользовательская приёмка v0.1.20 и исследование исходников.

## Подтверждено
1. В MAX Desktop существуют два разных транспортных протокола. NativeMaxTransport передаёт в SESSION_INIT userAgent.deviceType=ANDROID и appVersion/buildNumber из исследованного APK. NativeMaxWebSocketTransport передаёт deviceType=WEB и Windows/Chrome. Автоматическое подключение HybridMaxTransport предпочитает WebSocket через физическую сеть. У каждого сохранённого аккаунта свой тип транспорта, восстановление выбирает его по полю Transport; сама установка новой версии не превращает WEB-сеанс в TCP-сеанс.
2. Кнопка OPEN_APP отправляет BOT_WEB_APP(160) по уже авторизованному каналу и открывает server-signed HTTPS URL в изолированном WebView2 (Windows). Отправка через мобильный TCP и отображение в Windows WebView2 — две отдельные среды; они не становятся одинаковыми из-за смены User-Agent.
3. Адрес запуска MAX содержит WebAppPlatform (web/desktop/android/ios); WebAppData содержит подписанные данные входа. Источник: https://dev.max.ru/docs/webapps/bridge и https://dev.max.ru/docs/webapps/validation . WebAppPlatform в URL, приложение в WebView2 и сведения о доверенном устройстве нельзя смешивать.
4. На скриншоте приёмки v0.1.20 сервис «Коды подтверждения» отвечает «Данная функциональность доступна только в мобильной версии приложения» — это ответ конкретного сервиса после загрузки подписанного адреса. По одному снимку нельзя доказать, что проверяется только User-Agent, только WebAppPlatform или дополнительно серверное доверенное устройство.
5. Официальная документация MAX о привязке устройства для кодов подтверждения описывает штатные способы через Mobile ID и 2FA+SMS: https://help.max.ru/help/gosuslugi/svyazka_gosuslug_s_max/kak_smenit_doverennoe_ustroistvo_dlya_vhoda_v_gosuslugi . Не считать смену браузерного отпечатка эквивалентом такой проверки.

## Реализованная диагностика (не подмена платформы)
- HybridMaxTransport.ActiveProtocolLabel отражает реально активный TCP(Android) или WebSocket(WEB), с типом маршрута.
- Главная форма показывает протокол только активного авторизованного аккаунта, не меняя его сеанс.
- MaxMiniAppLaunchEnvironment.PlatformDescription читает лишь несекретный WebAppPlatform из уже возвращённого URL. Никаких изменений WebAppData, User-Agent, платформы в URL, Device ID, токенов или запроса 160 не выполняется.
- Окно мини-приложения показывает заявленную сервером платформу, не отображая полный подписанный URL.
- Автоматические тесты используют искусственные адреса и проверяют определение web/android/отсутствующей платформы.

## Ограничения и принципы
- Требование «выглядеть как мобильное» для интерфейса допустимо, но визуальная адаптация не является подтверждённой мобильной идентичностью.
- Для функциональности просмотра кодов и операций с доверенным устройством не подделывать платформу запуска или подписанные параметры ради обхода ограничения. Действовать только через предусмотренное MAX подтверждение устройства.
- Не изменять системный VPN, настройки DNS, системный прокси. Не включать отправку обычных сообщений.
- Протоколы, учётные записи, сообщения и безопасность обновлением не мигрировать без прямого согласования.

## Что проверять при следующей приёмке
1. Под аккаунтом отображается «Протокол: ... WEB ...» либо «... TCP / Android ...».
2. По нажатию «Посмотреть код» в заголовке мини-приложения отображается метка «Платформа запуска в URL: ...» (без WebAppData).
3. Если статус «web» при TCP(Android), доказано расхождение *транспорт vs URL-платформа*, но не доказана возможность доступа к защищённой функции.
4. Если «android» и сервер всё равно запрещает просмотр, необходима штатная процедура доверенного устройства; простое исправление браузера не решит её.
5. Фактическая поддержка мобильных мини-приложений остаётся отдельной задачей для незакрытых функциональных сценариев.
