# MAX Desktop — детальное исследование штатной проверки Mobile ID в MAX Android

Дата: 27.10.2026. Исходный APK: `ru.oneme.app`, MAX 26.35.1, `versionCode=6867`, SHA-256 `e809176d6bf6ff69247274433ec170a5db8a5687a02a04299a78a2ae978119fc`.

**Метод:** статическая декомпиляция оригинального APK посредством JADX в GitHub Actions. Исследованы 24 272 Java-файла. Исследование не запускало MAX, не обращалось к реальным аккаунтам, операторам и не подменяло ответы.

## Результат исследования

В оригинальном Android MAX подтверждён **отдельный внутренний мост WebAppVerifyMobileId**, через который мини-приложение просит Android выполнить проверочный HTTP-запрос с использованием доступной **сотовой сети**. Это не вызов Android API для чтения номера SIM и не обычное поле номера пользователя.

## 1. Формат обращения мини-приложения

`defpackage/eol.java` (строки 11–14) сериализует модель `one.me.webapp.domain.jsbridge.delegates.private.WebAppVerifyMobileIdRequest` с обязательными полями:
- `requestId: string` — идентификатор запроса.
- `url: string` — проверочный адрес, выбранный сервисом мини-приложения.

`defpackage/gol.java` содержит эти два поля. Номера телефона, IMEI, IMSI и ICCID в модели запроса **нет**.

`defpackage/zik.java` определяет вид действия `VERIFY_MOBILE_ID`, имя `WebAppVerifyMobileId` и внутренний ключ `verify_mobile_id`.

`defpackage/dol.java` (строки 28–47, 76–183) является обработчиком внутри моста мини-приложения. Он десериализует JSON с указанными полями, создаёт операцию с URL и запускает асинхронную обработку.

## 2. Как выбирается сотовая сеть

`defpackage/ekl.java` (строки 279–302) получает `ConnectivityManager` и регистрирует запрос сети:
- `NetworkRequest.Builder().addTransportType(0).addCapability(12).build()`.
- В Android `TRANSPORT_CELLULAR = 0`; `NET_CAPABILITY_INTERNET = 12`.
- `ConnectivityManager.requestNetwork(...)` выбирает подходящее сотовое подключение и уведомляет приложение о доступной сети через обратный вызов.

`defpackage/fcl.java` — реализация `WebAppHttpClient`. Она хранит `Network` и сетевой клиент, связанный с зарегистрированной сотовой сетью. В методе `a(url, ...)` (строки 65–84) используется этот клиент для HTTP-запроса по переданному URL.

В `fcl.java` (строки 72–75) при отсутствии сотового клиента либо выключенном мобильном подключении создаётся `WebAppHttpClient$WebAppNoNetworkException`. Есть также обработка некоторых сетевых ошибок (включая `EPERM`), но её условия необходимо оценивать без утверждения о гарантированном обходном маршруте.

Официальные определения:
- https://developer.android.com/reference/android/net/NetworkRequest.Builder
- https://developer.android.com/reference/android/net/ConnectivityManager
- https://developer.android.com/reference/android/net/Network

## 3. Возврат результата мини-приложению

`defpackage/qrk.java` (ветка 13, строки 587–635) вызывает `fcl.a(url,...)`, затем формирует `ajk` с:
- `code`: HTTP-код;
- `headers`: заголовки HTTP-ответа;
- `data`: тело ответа, передаваемое в Base64.

`defpackage/jol.java` и `hol.java` определяют модель `WebAppVerifyMobileIdResponse`: `requestId`, `statusCode`, `headers`, `data`.

`defpackage/a8l.java` (ветка 16, строки 624–650) сериализует эту модель и посылает приватное событие `WebAppVerifyMobileId` обратно в мини-приложение.

`defpackage/qrk.java` (ветка 17, строки 715–730) отдельно обрабатывает исключения: `cancelled` для отмены и `no_cellular` для `WebAppNoNetworkException`. Прочие ошибки проходят в обобщённую обработку.

**Важно:** HTTP `statusCode` в модели — статус сетевого запроса, а не автоматическое утверждение «устройство стало доверенным». Итоговую политику привязки определяет сервис.

## 4. Проверка наличия номера SIM

Полный статический поиск по 24 272 файлам не нашёл `TelephonyManager.getLine1Number`, `SubscriptionManager.getPhoneNumber`, `getSubscriberId` и `getSimSerialNumber` в декомпилированных классах. `getNetworkOperator()` и `getSimOperator()` обнаружены, но они относятся к сведениям об операторе.

Эти результаты не исключают всех нативных или динамических сценариев, но доказывают, что **исследованный путь WebAppVerifyMobileId не передаёт телефонный номер как отдельное поле**. Телефон аккаунта уже известен MAX Desktop в `MaxSavedSession.Phone`. Его повторное копирование в значение «SIM» не создаёт сотовую сеть и не подтверждает номер у оператора.

Примеры операторских HTTP-узлов найдены в `res/xml/network_security_config.xml`. Наличие доменов не означает, что каждый действительно используется в этом сценарии. Это согласуется с операционными механизмами Mobile ID/HE-auth, но окончательное участие конкретного оператора потребовало бы отдельного динамического наблюдения на своём устройстве.

## 5. Почему MAX Desktop не может выполнить тот же сценарий

По пользовательской приёмке v0.1.21:
- авторизованный MAX-протокол — TCP/Android по физической сети;
- подписанная сервером платформа мини-приложения — `WebAppPlatform=android`;
- после загрузки мини-приложение требует привязки устройства и мобильного интернета с нужной SIM;
- по оценке пользователя индикатор показывается около 1–2 минут.

В нашей реализации `src/MaxDesktop.App/MiniAppWindow.cs` мини-приложение работает внутри Windows WebView2, а `AreHostObjectsAllowed=false` и `IsWebMessageEnabled=false`. **Приватный мост `WebAppVerifyMobileId` не реализован.** Даже наличие Android/TCP-сеанса не создаёт Android `ConnectivityManager`, `TRANSPORT_CELLULAR` и подтверждённую операторскую SIM-сеть.

Следовательно, подмена User-Agent, WebAppPlatform, номера телефона или ответа оператора не является корректной реализацией штатного механизма.

## 6. Причина задержки 1–2 минуты

Доказано, что начальная навигация WebView2 до мини-приложения завершается. Не доказано, какая последующая операция занимает 1–2 минуты.

Возможные гипотезы (без присвоения статуса факта): ожидание ответа внутреннего моста, время ожидания проверки сервиса, тайм-аут сетевого запроса или изменение состояния доверенного устройства. В исследованных `ekl/fcl/qrk` нет подтверждённого фиксированного тайм-аута, равного наблюдаемой задержке.

Для уточнения допустима локальная диагностика только времён этапов, ошибок без персональных полей и событий загрузки, без сохранения URL, заголовков, тела Mobile ID, кодов и WebAppData.

## 7. Штатный пользовательский путь и ограничение Desktop

Официальная справка MAX описывает привязку доверенного мобильного устройства через Mobile ID, а при настроенной двухфакторной аутентификации — сценарий подтверждения через СМС:
https://help.max.ru/help/gosuslugi/svyazka_gosuslug_s_max/kak_smenit_doverennoe_ustroistvo_dlya_vhoda_v_gosuslugi

Владелец сообщил, что вариант СМС **не отображается в текущем мини-приложении MAX Desktop**. Не следует объявлять эту возможность доступной на ПК без отдельного подтверждения.

Для прямого просмотра защищённых кодов на ПК требуется разрешённая MAX поддержка доверенного настольного устройства, которая текущим исследованием не установлена. Возможность USB-модема с SIM сама по себе не доказывает совместимость с Android-мостом и серверными правилами MAX.

1. Есть ли документированный оператором MAX сценарий привязки именно ПК без имитации мобильного устройства?

3. Можно ли применять легитимную мобильную авторизацию для **обычных** функций MAX Desktop, не создавая ложного доверенного устройства?
4. При необходимом испытании на телефоне с собственной SIM — какие статусы и тайминги показывают клиент/сервис, если не публиковать запрос, ответ и персональные данные?

- Действующие сеансы MAX Desktop не перезаписывать.
- Системный VPN, DNS и маршрутизацию пользователя не менять.
- Сервисные URL Mobile ID, секреты оператора, токены, заголовки, коды и WebAppData не публиковать.
- Не подделывать ответы оператора, SIM, доверенное устройство или серверные подписи.
