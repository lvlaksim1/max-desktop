# MAX Desktop — исследование JavaScript-моста и вложенных кадров
Дата: 27.10.2026. **Статус:** доказательно обнаружено отличие клиентов; *причина отказа при отображении кодов ещё не доказана*.

## Исходная приёмка
В MAX Desktop v0.1.23 у пользователя на экране «Проверяем номер телефона» не появлялся настоящий код. Строка «MAX Bridge активен» отображалась после `miniapp-bridge-ready`, отправленного **нашим собственным** сценарием при внедрении в основной документ. Нельзя интерпретировать эту строку как вызов интерфейса самим мини-приложением. Проверка на реальном Android с работающим оригинальным MAX показала подлинный код **без новой привязки**; этот Android ранее уже использовался для кодов.

Физический Android: ADB PASS, mobile_data=1, Wi-Fi=0, LTE; через PC Gateway #491 найдены сотовые сетевые агенты с INTERNET и VALIDATED. Сетевые условия есть, но новая Mobile ID операция и её переносимость в Windows не доказаны.

## 1. Регистрация на оригинальном Android
Декомпилированный APK MAX 26.35.1, `defpackage/pil.java`:
- `addJavascriptInterface(new jql(...), "WebViewHandler")` — безусловно.
- `addJavascriptInterface(new koe(...), "PrivateWebViewHandler")` — только при условии `webAppRootScreen.N1().Z`. Значение и серверное назначение флага `Z` для конкретного запуска по статическим фрагментам не установлены.
- `jql.postEvent(name,body)` вызывает `ekl.j1(name,body,false)`, `koe.postEvent(name,body)` — `ekl.j1(name,body,true)`.

Официальный Android API прямо указывает: `addJavascriptInterface` размещает интерфейс **во всех кадрах WebView, включая iframe**. Это важная техническая разница по сравнению с нашим фильтром.

Ссылки:
- https://developer.android.com/reference/android/webkit/WebView#addJavascriptInterface(java.lang.Object,java.lang.String)
- https://github.com/lvlaksim1/max-android-research/blob/main/docs/webapp-jsbridge-inspection-26.35.1.md

## 2. Два маршрута в публичном MAX WebApp SDK
Исследованный `https://st.max.ru/js/max-web-app.js` (публичная библиотека, не закрытый сценарий бота):
- Если библиотека определяет, что работает во вложенном кадре, `sendOverIframe` посылает событие родителю через `window.parent.postMessage`.
- В основном документе при существовании `window.WebViewHandler` используется `sendOverWebView` → `WebViewHandler.postEvent(name,JSON.stringify(body))`.
- Приватный `WebAppVerifyMobileId` **не присутствует** в публичной библиотеке. Нельзя заключить из поведения публичной библиотеки, каким именно способом закрытое мини-приложение вызывает приватную проверку.

Декомпилированные сведения:

## 3. Текущий Windows MAX Desktop
`src/MaxDesktop.App/MiniAppWindow.cs` использует `CoreWebView2.AddScriptToExecuteOnDocumentCreatedAsync`: WebView2 умеет применять этот сценарий к основному документу **и вложенным кадрам**, но **наш собственный код** сразу выходит при `window !== window.top` либо `location.origin !== signedOrigin`. Поэтому во вложенных кадрах интерфейс действительно отсутствует.

Соответственно сценарий может не заметить события:
- если источник события — отдельный iframe и используется публичный `postMessage` к родителю;
- если закрытая часть работает в кадре или документе с другим origin;
- если приватный интерфейс вообще не используется на данном шаге и проверка идёт на сервере.

**Все три варианта остаются гипотезами для реального интерфейса бота.** Количество кадров само по себе не говорит, откуда пришёл запрос или доверяет ли сервер устройству.

Источники:
- https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2.addscripttoexecuteondocumentcreatedasync
- `src/MaxDesktop.App/MiniAppWindow.cs`, по состоянию после 27.10.2026.

## 4. Подтверждаемая ошибка диагностики и изменение исходников
Исправлено (исходники **без нового пользовательского релиза**):
- Не использовать формулировку «Интерфейс MAX Bridge активен» только по сообщению собственного скрипта. Теперь это «Наш сценарий интерфейса внедрён; вызов Mobile ID со стороны MAX не наблюдался».
- Считать **только количество созданных вложенных кадров** по `CoreWebView2.FrameCreated`. Значение не является числом активных кадров: между событиями они могут закрыться.
- Изменить формулировку успешного `ExecuteScriptAsync`: это вызов функции приёма в мини-приложении, а не принятие решения сервером.
- Добавить офлайновую проверку встроенного JS-кода на синтетических документах: самосообщение без вызова MAX, отсутствие инъекции во вложенных кадрах и при ином origin, исключение несвязанных событий; CI работает без аккаунта и сети.

Тест: `tests/MaxDesktop.MiniAppBridge.Smoke/bridge.test.cjs`, запуск `node --test ...`; включён в Windows CI.

## 5. Как продолжить
1. Дождаться успешного Windows CI исходников и тестов, **не заявлять** решение вопроса кодов на основании прохождения теста.
2. Следующее реальное наблюдение Windows, если понадобится, должно различить наличие вложенных кадров и факт обращения мини-приложения к мосту. Не записывать URL, DOM, HTTP тела, SMS, значения кодов, сеансы и доказательства оператора.
3. Для серверного подтверждения использовать только штатную проверку на доверенном устройстве и документированный вариант SMS при включённой 2FA, если он действительно предложен сервером. Ни автоматическая подмена операторского ответа, ни извлечение защищённого кода с экрана Android в этот тест не входят.
4. При непереносимой серверной привязке честно сохранить результат; не обещать код на Windows, пока сервер фактически не разрешил это.

**Критерий конечной работы MAX Desktop остаётся прежним:** настоящий защищённый код отображается в окне Windows после принятой сервером проверки. Исследование кадров и офлайновые тесты — только промежуточные технические результаты.
