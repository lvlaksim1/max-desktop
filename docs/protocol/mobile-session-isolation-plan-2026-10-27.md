# MAX Desktop — проверка v0.1.21 и схема мобильных сеансов (27.10.2026)

## Факт пользовательской проверки
На снимке v0.1.21 под активным аккаунтом указано **WebSocket / WEB / физическая сеть**. В окне мини-приложения «Посмотреть код» отображается **WebAppPlatform=web**. Приложение сервиса корректно загружается по подписанному BOT_WEB_APP URL, затем показывает: «Данная функциональность доступна только в мобильной версии приложения».

Это подтверждает веб-тип конкретного активного сеанса и веб-платформу в полученном URL. Не доказывает, что изменение только User-Agent решит проблему: данные подписываются/выдаются сервером, а бот может независимо проверять доверенное устройство. Источники платформы: https://dev.max.ru/docs/webapps/bridge; https://dev.max.ru/docs/webapps/validation .

## Исходники: риски переключения существующего сеанса
- HybridMaxTransport.BeginLoginAsync в Automatic предпочитает WEB_PHYSICAL. NativeMaxTransport использует deviceType=ANDROID, но его наличие не делает сохранённый WEB-сеанс мобильным.
- HybridMaxTransport.RestoreSessionAsync использует session.Transport и не мигрирует сеанс по изменению предпочтения.
- ProtectedMaxAccountVault индексирует аккаунты по Phone, метод Upsert **перезаписывает** запись с тем же номером, независимо от session.Transport. Простая новая авторизация номера по TCP может заменить рабочий WEB-токен.
- Прямое изменение Transport с WEB на TCP невалидно: это другой протокол и контекст аутентификации. Нельзя менять тип сохранённого сеанса без подтверждённого нового входа.
- Встроенный WebView2 — Windows; нельзя утверждать, что мобильный TCP гарантирует WebAppPlatform=android или делает устройство доверенным.

## Проектирование следующей безопасной итерации
1. Разделить устойчивые слоты (phone, transportFamily, sessionId) вместо единственного phone; мигрировать текущие записи без потерь, сохранять резервную копию зашифрованных данных.
2. Добавлять мобильную TCP-авторизацию как отдельный явно выбранный сеанс, не заменяющий работающий WEB. Не инициировать SMS без действия владельца.
3. Предоставить выбор между WEB и мобильным TCP для обычных чатов/истории; использовать платформенный тип согласно реальному подтверждённому сеансу, не подделывать WebAppData.
4. После успешной реальной авторизации мобильного сеанса проверить документированный ответ BOT_WEB_APP и реальную платформу. Отдельно учитывать условия доверенного устройства.
5. Функциональность «Коды подтверждения» должна следовать штатной проверке устройства MAX. Документация: https://help.max.ru/help/gosuslugi/svyazka_gosuslug_s_max/kak_smenit_doverennoe_ustroistvo_dlya_vhoda_v_gosuslugi — проверка через Mobile ID или настройку 2FA и SMS на соответствующем мобильном устройстве. Не обходить это подменой User-Agent, подписями, DeviceId.

## Статус
v0.1.21 пользовательски подтверждена в части диагностических меток. Само ограничение просмотра кодов остаётся. Изменений в рабочий код по этому исследованию не внесено; текущий последний выпуск v0.1.21 сохраняется.
