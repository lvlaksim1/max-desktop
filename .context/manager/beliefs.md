## Постоянные данные
- [GitHub] Публичный репозиторий `lvlaksim1/max-desktop`, продукт и состояние менеджера в `main`; менеджер с постоянным `manager_id=project-manager`, Project Manager v2; Windows .NET 8/WPF, установка и обновления по образцу MailRu Desktop.
- [Владелец] QR-авторизация исключена. Нужен вход обычного аккаунта MAX по номеру/SMS и, если сервер требует, 2FA. Не предлагать QR при возобновлении.
- [Владелец] Крестик главного окна → трей; «−» → панель задач; правый клик по трею → «Выход»; повторный запуск не создаёт второй экземпляр. [Исходники/CI] Эти сценарии реализованы, но пользовательская GUI-приёмка не подтверждена.
- [Исходники] TCP-транспорт и независимый WEB JSON/WebSocket v11 через .NET и Chromium WebView2; выбор «авто / Edge / .NET / TCP». Сохранённые сеансы Windows защищены DPAPI, старые TCP/WEB поддержаны. При неясном результате SMS не дублировать запрос через другой транспорт.
- [GitHub CI] Анонимный INIT по TCP/.NET и Chromium WebView2 работал на серверах GitHub Windows **из другой сети**. Офлайн-испытания имитации SMS→код→LOGIN прошли, но реальная доставка SMS и вход пользователя не подтверждены.

## Проверенная причина остановки работ с авторизацией
- [Владелец, скриншоты v0.1.8] Все режимы входа прерываются **до INIT / AUTH_REQUEST и до передачи номера**: TCP → TLS_HANDSHAKE/EOF (всего 9 попыток через системный прокси и напрямую), .NET WebSocket → WS_CONNECT / TLS-EOF, Chromium WebView2 → WS_CONNECT без открытия соединения, автоматический режим повторяет отказ Edge.
- [Владелец, браузер] В Яндекс Браузере при обращении к `https://ws-api.oneme.ru/websocket?utm_source=chatgpt.com` соединение неожиданно прервано, HTTP-ответа на скриншоте нет.
- [Владелец, PowerShell] На **том же компьютере** `curl.exe -I --max-time 15 https://ws-api.oneme.ru/websocket` (без UTM-параметра) возвращает **`curl: (35) schannel: failed to receive handshake, SSL/TLS connection failed`**.
- [GitHub Actions Runner, 26.10.2026] На удалённом Windows Runner проверка curl.exe с тем же HTTP HEAD и адресом https://ws-api.oneme.ru/websocket завершилась с кодом 0 и HTTP 403 (запуск 40315701059), а с компьютера владельца ранее получен код 35/Schannel. Различие условий подключения подтверждено; точная причина локального отказа неизвестна. Повторные TCP и WebSocket проверки успешны (40248116311, 40253115470, 40255463057).
- **Подтверждено:** TLS-сбой воспроизводится вне MAX Desktop. Ошибка сериализации SMS или только нашего сетевого модуля не объясняет независимый браузерный/curl отказ.
- **Не подтверждено:** конкретный источник — провайдер, DNS, локальный VPN/прокси, фильтрация по SNI, сетевой экран/антивирус, системная настройка TLS либо инфраструктура MAX. Нельзя заявлять единственную доказанную первопричину.
- **Исправленный порядок:** сначала независимая проверка с **того же ПК в другом интернет-канале** (например, мобильная точка доступа); затем адресное исправление по результату. Предыдущая методическая ошибка — многократная смена транспорта и сертификатов на основании успехов CI из другой сети без проверки локальной доступности.
- [GitHub] Последний выпущенный релиз — **v0.1.8**, Setup/Update/SHA-256; успешная сборка и выпуск Actions 40255959364 / 40255959472. **v0.1.9 не выпускалась**. Техническая оценка: `docs/protocol/network-root-cause-2026-10-26.md`.

## Новое условие владельца и подтверждённая локальная диагностика VPN (26.10.2026)
- [Прямое указание владельца] На компьютере постоянно включён системный VPN. **Отключать VPN нельзя; MAX Desktop должен работать при включённом VPN**. Не запрашивать его отключение или обязательный переход на другую сеть.
- [GitHub, подтверждено] Для исполнения заданий именно на ПК владельца используется приватный `lvlaksim1/pc-runner-gateway`: Windows self-hosted runner `pc-gateway-primary`, приватные запросы GitHub Issues и зафиксированные SHA проектных скриптов. Репозиторий MAX зарегистрирован в списке разрешённых клиентов, установлен официальный Client Kit 1.2, первые запросы №392/393 успешны.
- [Раннер ПК владельца, запросы №394, №395] Имя `ws-api.oneme.ru` разрешается в два IPv4, TCP 443 достижим, но HTTPS к `ws-api.oneme.ru` и `web.max.ru` даёт `curl 35`. `github.com`, `mail.ru`, `www.microsoft.com` возвращают HTTP 200. Через системный HTTP-прокси MAX снова даёт `curl 35`, а контрольные сайты — HTTP 200.
- [Раннер ПК владельца, запрос №396] HTTP CONNECT через настроенный прокси для MAX возвращает 200, но последующее TLS соединение обрывается (`curl 35`) при автоматическом TLS, отдельно TLS 1.2 и TLS 1.3. Для GitHub тот же прокси даёт CONNECT 200 и HTTP 200.
- [Раннер ПК владельца, запрос №397] Системный прокси расположен локально, обслуживается процессом `xray`; обнаружен TUN-интерфейс. [Запрос №398] конкретная управляющая программа Xray не идентифицирована. Указанные данные не доказывают, какая сторона обрывает TLS; вероятны выбор маршрута Xray/удалённый выход VPN/избирательная фильтрация/политика MAX.
- [Инвариант] При последующих действиях не менять конфигурацию VPN, прокси, маршрутов и DNS без отдельного обоснования и согласования. Прямое приложение подключение также может идти через TUN, поэтому не считать его гарантированным обходом сетевой проблемы.

## Вход в официальном MAX без 2FA и отказ WEB (26.10.2026)
- [Свидетельство владельца] В оригинальном приложении MAX авторизация проходит без капчи и запроса 2FA. Устройство и тип официального приложения (Android/iOS/Windows), а также наличие старого доверенного сеанса не уточнены. Нельзя на основе одного наблюдения делать вывод, что политика WEB-входа одинакова.
- [Снимок v0.1.12] MAX Desktop после реального SMS/кода получил `WS_CHECK_CODE: Логин ограничен. Требуется установить 2FA`. Это явный отказ серверного протокола WEB (opcode 18), а не ошибка TLS/капчи и не доказательство того, что код ошибочный.
- [Официальная справка MAX, прочитана 26.10.2026] https://help.max.ru/help/account/dostup_k_prophilyu/kak_voiti_v_prophil_max_esli_on_uzhe_est сообщает: при наличии активной сессии на другом устройстве и отсутствии настроенного «Пароля для входа» (2FA) вход в ещё одно устройство может быть разрешён только после установки пароля на уже авторизованном устройстве. https://help.max.ru/help/account/zashshita_prophilya/kak_ustanovit_ili_otklyuchit_parol_dlya_vhoda_v_max уточняет, что пароль устанавливается на стороне аккаунта, не через WEB.
- [Вывод] Не утверждать, что это обязательно ошибка реализации MAX Desktop, или что оригинальное приложение точно обходится без 2FA при подключении **нового** устройства. Нужно установить, сравнивались ли свежие входы и один тип доверия к устройству. Не подменять идентификатор устройства и не пытаться обходить защитное требование; продолжать исследование только допустимых официально поддерживаемых сценариев. Не требовать 2FA от владельца, пока это не согласовано.

## Первый подтверждённый реальный LOGIN MAX Desktop (26.10.2026, владелец)
- [Владелец и снимки с Android] При подключении **второго устройства** к аккаунту MAX без ранее настроенного пароля сервер требует установить «Пароль для входа» на уже авторизованном Android-устройстве. На существующем устройстве при попытке установки пароля MAX сообщает, что установка возможна только **через сутки**. Это серверный временной запрет, а не дефект TLS, SMS или кода MAX Desktop. Конкретный момент снятия ограничения не измерен.
- [Владелец, новый независимый аккаунт] При подключении другого аккаунта, где 2FA/пароль был установлен заранее, MAX Desktop запросил дополнительный пароль. Владелец ввёл его; сервер подтвердил вход. Скриншот приложения v0.1.13 показывает «MAX подключён» и статус «Авторизация MAX подтверждена». Номера телефонов и прочие личные сведения не сохранять в репозитории.
- [Проверка исходного кода] NativeMaxTransport.SaveAuthenticatedLoginAsync сначала выполняет LOGIN через сервер, затем защищённо записывает MaxSavedSession через Windows DPAPI, после чего переводит State в Connected; MainWindow применяет состояние Connected и показывает подтверждение. Таким образом, один реальный LOGIN доказан, хотя **восстановление сеанса после перезапуска ещё не проверено**. На снимке не видно выбранного в окне входа способа подключения, поэтому конкретный транспорт успешного входа по снимку не устанавливается.
