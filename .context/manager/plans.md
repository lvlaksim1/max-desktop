2. В v0.1.11 при вводе SMS-кода окно показывало старое сообщение «Запрос принят» независимо от результата сервера. Исправлено в v0.1.12: отображение WS_CHECK_CODE/WS_LOGIN, очистка незавершённой авторизации при закрытии окна. Build 40340814912 и release 40341203011 завершились успешно.
3. **Следующий шаг — установленная v0.1.12**: https://github.com/lvlaksim1/max-desktop/releases/tag/v0.1.12 . Один запрос SMS с ручным прохождением капчи, затем одно подтверждение кода. При успехе LOGIN закроет диалог и сохранит сеанс; при отказе увидеть конкретный этап. Не публиковать номер, код, токены или URL капчи.
4. По реальному безопасному сообщению разобраться в ответе сервера. Поддержка 2FA/поток LOGIN только по фактической форме ответа; не додумывать причину по прежней надписи.
5. После реального успешного LOGIN проверить восстановление DPAPI-сеанса, чаты/историю/отправку сообщений, вложения и уведомления.
6. Затем GUI-приёмка трея, кнопки «−», одного экземпляра, обновителя и сохранённых настроек.
7. GitHub Actions Windows Runner — сборка и имитационные проверки; для ПК владельца — только приватный pc-runner-gateway с pinned SHA, без TinyFish и без перенастройки VPN.

## Дополнение: выяснить различие авторизации (26.10.2026)
1. Новый факт: авторизация в оригинальном приложении MAX у владельца происходит без капчи и 2FA. Не известно, идёт ли речь о мобильном или настольном приложении и действительно новой сессии.
2. Прямой отказ нашего WEB протокола после CODE_ENTER: `Логин ограничен. Требуется установить 2FA`; WEB-транспорт сам не может считать это успешным LOGIN.
3. Официальная справка MAX связывает вход на новое устройство при наличии текущей сессии без пароля с необходимостью установки «Пароля для входа». Сначала сопоставить условия исходного и нового входа; не делать вывод о необходимости 2FA **во всех** условиях.
4. До установления фактов не предлагать обход серверной защиты, не менять fingerprint как метод обхода, не менять VPN, не выпускать новую версию только ради косметического ответа.
